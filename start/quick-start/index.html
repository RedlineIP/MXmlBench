Quick start

This walkthrough takes one merge from start to finish: git hits a conflict in an XML file, the merge driver resolves everything it safely can, and you settle the one real disagreement in the Workbench. It takes about ten minutes.

You need:

  • M-XML Bench installed with Register the XML merge driver with git and Make M-XML Bench the default git mergetool both checked, and the machine registered. Installing covers both.
  • git 2.28 or later, with user.name and user.email set, since the practice script makes commits.

1. Make a practice repo

Section titled “1. Make a practice repo”

Paste this into PowerShell. It creates a repo with one file, policy.xml, and two branches that each change it.

Practice repo script

The two branches touch many of the same lines. A line-based merge would stop on most of them. Only one change is a real disagreement: main sets the deductible to 250 and rates sets it to 750.

2. Merge

Section titled “2. Merge”

git hands policy.xml to the XML merge driver. The driver merges each element on its own, so it keeps main‘s new status, tier, limit and welcome text, and it takes the version number, the state and the new legal message from rates. It prints the one thing it could not decide, with both sides’ values:

The second line names the temporary file git gave the driver, and the name changes every time. git then reports the merge as conflicted. policy.xml now holds the merged file with one pair of conflict markers, around the deductible.

If the whole file came out as one conflict instead, with all of main above all of rates, this machine is not registered. See A manuscript came out as one big conflict.

3. Open the Workbench

Section titled “3. Open the Workbench”

The Workbench opens on policy.xml. The title bar reads git mergetool · policy.xml, and the ribbon’s status shows 1 conflict unresolved. If a different merge tool opens, see git mergetool opens a different tool.

The window has four panes:

  • ours is your branch, main. Read-only.
  • base is the version both branches started from. Read-only.
  • theirs is the branch you are merging in, rates. Read-only.
  • merged result is the file that will be written back. You can edit it.

git does not pass branch names to a merge tool, so the panes read ours and theirs. A few labels use git’s mergetool names, local for ours and remote for theirs. The window covers every part of the screen.

Why “ours” is main here

In a merge, ours is the branch you are on and theirs is the branch named in git merge. During a rebase git swaps the two, so the panes read the other way around. That is git’s own behavior, not the Workbench’s.

4. Check what the driver decided

Section titled “4. Check what the driver decided”

The Structural diff panel lists every element that changed and what the driver did with it. Each row has a verdict chip: merged where both sides’ changes were combined, took ours or took theirs where only one side changed it, and conflict where they disagree. Read down it before you resolve anything: this is where you would spot the driver keeping a change you did not expect.

The panel also counts unresolved fallbacks: groups of elements with no id or name, like the <v> inside each field, that the driver paired by position. You can leave them for this walkthrough. They never block saving, and Unresolved fallbacks explains when to look.

5. Resolve the conflict

Section titled “5. Resolve the conflict”

On the Merge tab, the CONFLICT readout shows which conflict you are on. It starts at 0 / 1: no conflict is picked yet, and the take buttons act only on the one you have stepped to. Press Next (→) to step to the deductible. The readout changes to 1 / 1. Then pick a side:

Action Ribbon Key
Keep ours (250) Take ours O
Keep theirs (750) Take theirs T
Keep both, ours first Take both B
Keep both, theirs first Take both menu, Theirs first Shift+B
Undo the last pick Undo U

The letter keys work anywhere except the merged pane, where they type as in any editor. You can also click the conflict chip in the Structural diff and choose there, or type the value you want straight into the merged pane. Resolving conflicts covers every way.

For this walkthrough, press Take ours to keep the 250 deductible. The row’s chip changes to resolved, and the ribbon’s status changes to no conflicts.

6. Save and finish

Section titled “6. Save and finish”

Check that the ribbon reads no conflicts, then press Save & finish. The Workbench checks that no conflict markers are left and that the result is well-formed XML, writes it to policy.xml, and closes. git marks the file resolved.

The Conflict report tab below the panes lists what the driver found when the merge opened. It does not change as you resolve, so it still lists the deductible after you pick a side.

If you need to stop partway, Keep for later saves your progress. The next git mergetool on the same file picks up where you left off, as long as the merge inputs have not changed. git prints merge of policy.xml failed when you keep for later; that is expected. Saving and finishing has the details.

7. Commit

Section titled “7. Commit”

git may have left a policy.xml.orig backup next to the file. That comes from git’s mergetool.keepBackup setting, not from M-XML Bench, and you can delete it.

Other ways to open a merge

Section titled “Other ways to open a merge”

You do not have to start from git mergetool. Opening a merge covers each way.

  • Open the Workbench from the Start menu and choose Three files to pick a base, ours and theirs file yourself.
  • Choose From git to pick a repo and one of its conflicted .xml files.
  • Launch from your editor or git client. Git clients covers VS Code, JetBrains, Sourcetree, TortoiseGit and others.
