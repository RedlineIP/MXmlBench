Reporting bugs

Report a bug either way:

  • On GitHub, in public. Open the new issue page and pick Bug report. You need a GitHub account.
  • By email. Send the same details to support@redlineip.com if you would rather not post in public or have no GitHub account.

Issues are public

Keep client content out of every field, the title included. Never attach manuscripts or defect report zips; email them to support@redlineip.com instead.

Find your version

Section titled “Find your version”

Open Settings > Apps > Installed apps. The entry shows the version, for example M-XML Bench version 0.9.7. The setup file name has it too: MXmlBench-Setup-0.9.7.exe.

What to include

Section titled “What to include”
  • What you did, what happened, and what you expected.
  • Where it happened: during a git merge (the merge driver), in the Workbench, in setup, or while registering.
  • Your git client, if one opened the Workbench.
  • Any error text, pasted as text.

Describe the elements involved, not the client’s content. Leave out client and carrier names, product and program codes, rate and table values, and file, repository and branch names.

When the merge driver decides wrong

Section titled “When the merge driver decides wrong”

Report a wrong merge decision from the Workbench:

  1. In the Structural diff panel, right-click the element’s row, or click its verdict chip, and choose Report driver defect. Then pick what the driver should have done, for example Taken local or Flagged a conflict. Each pick adds a check.
  2. Open the Case tab in the drawer below the panes. It lists each check, such as …/private[@id=‘deductible’] should have taken local. Fix the merged result the way it should have come out, add a note for the engineer if it helps, then press Review & submit →.
  3. On the Review & submit sheet, press Submit case. This saves a zip in %LocalAppData%\MXmlBench\outbox; paste that path into File Explorer’s address bar to open the folder. Nothing is sent from your machine.
  4. Email the zip to support@redlineip.com, with the issue number if you opened one.

Review & submit → stays unavailable until the case has at least one check. It is also unavailable in a text merge, since git’s line merge made that result, not the driver. A check that says the driver should have merged cleanly needs the conflict markers resolved first.

The zip holds:

  • base.xml, ours.xml and theirs.xml, the three inputs.
  • output.xml, what the driver wrote.
  • expected.xml, your corrected result from the merged pane.
  • case.json, your checks and where the merge came from.
  • rule-note.md, your note and the driver version.

What case.json records about where the merge came from depends on how you opened it:

Opened with Recorded
From git on the start screen The repository path, both branch names, the merge base and the file name
Three files on the start screen The full paths of the ours and theirs files
git mergetool Only the file name

Treat the zip as confidential. To see what case.json records before you send it, open engineer details (case.json) on the Review & submit sheet.

How samples are handled

Section titled “How samples are handled”

A sample is used only to reproduce and fix the bug, then deleted. Samples are never published.

If you cannot share a client file, cut the manuscript down to the elements involved and rename ids and values. The bug often still reproduces.

Posted something confidential?

Section titled “Posted something confidential?”

Email support@redlineip.com with the issue link right away so the issue can be deleted. Editing it yourself is not enough: GitHub keeps every edit in the issue’s history.

Security problems

Section titled “Security problems”

Report these privately, never in an issue: file a private vulnerability report or email support@redlineip.com.
