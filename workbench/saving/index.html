Saving and finishing

How a merge ends depends on how it started. Under git mergetool, the result goes back to git. Opened from the start screen, it goes to a file you choose.

Under git mergetool

Section titled “Under git mergetool”

The right end of the ribbon has two buttons: Keep for later and Save & finish.

Save & finish

Section titled “Save & finish”

Save & finish (Ctrl+S) writes the merged result to the file git is waiting on, then closes the window. It checks two things first:

  1. No conflict markers are left. While any conflict is open the button is grayed out, and hovering it says how many remain. A stray marker line you missed while editing counts too.
  2. The result is well-formed XML. This applies to manuscripts, and to any XML file merged as text. If the check fails, the ribbon says Not written: the result is not well-formed XML at line 12, column 5, followed by the parser’s reason, and the merged pane marks the spot.

When both pass, the ribbon shows Written to policy.xml and the window closes. The Workbench tells git the merge succeeded, and git marks the file resolved. Commit when every file is done.

Unresolved fallbacks never hold up saving.

Keep for later

Section titled “Keep for later”

Keep for later stores the merged result as it is, markers included, and closes the window. git reports the file as failed, for example merge of policy.xml failed, and leaves it conflicted. That is expected.

The next git mergetool on the same file opens where you left off, and the ribbon says Resumed the merge you kept for later. Reload on the Session tab then becomes a menu:

  • Reload kept merge goes back to what you kept.
  • Start over from git’s inputs deletes the kept merge and runs the driver again. The Workbench asks first.

A kept merge belongs to one set of inputs. If the branches changed since, for example after you aborted and restarted the merge, the Workbench runs the driver fresh and says A kept merge for policy.xml belongs to different inputs and was ignored.

Kept merges live in %LocalAppData%\MXmlBench\mergetool. Uninstalling with Also remove your M-XML Bench data deletes them.

Closing the window

Section titled “Closing the window”

Closing without saving asks what to do with the file, under the title Leave the merge unresolved:

You have The choices
Not edited anything Exit to git leaves the file conflicted. Back returns to the merge.
Edited the merged result Keep for later, Discard & exit, or Back.

Either way git reports the file as failed and leaves it conflicted.

Saved the wrong result?

Section titled “Saved the wrong result?”

Until you commit, you can redo the merge of one file. Run:

git runs the XML merge driver again and puts the conflict back, as if the merge had just stopped. Then run git mergetool and resolve it again. Anything you changed in that file since the merge is replaced.

What git sees

Section titled “What git sees”

The Workbench exits with 0 only after Save & finish writes the file. Closing, cancelling and Keep for later exit with 1. A bad command line or an error exits with 2. Git clients explains how clients use these codes.

From the start screen

Section titled “From the start screen”

A merge opened with Three files or From git has Save result at the right end of the ribbon, and Save as on the Session tab. Both open a save dialog, Save merged result, that suggests the ours file, or under From git the conflicted file in the repository. Ctrl+S does the same.

These saves are not held up by open conflicts: the markers are written as they are. The ribbon says what was saved:

Message Meaning
Saved The result was written, with no conflicts left.
Saved with 2 unresolved conflicts The file has conflict markers in it.
Saved, but the result is not well-formed XML at line 12, column 5 The file was written, but Duck Creek will not load it until the problem is fixed. The merged pane marks the spot.
Save failed: and a reason Nothing was written.

Opened with From git

The save dialog suggests the conflicted file in the repository. Saving over it does not mark it resolved in git: once it has no conflicts left, run git add on it yourself.

Resume a partial save

Section titled “Resume a partial save”

When a save leaves conflicts open, the Workbench writes a session file next to it, named after the saved file with .mxml-session.json on the end, and adds the save to Recent marked resume. Open that entry to pick up where you stopped. Opening the saved file as ours under Three files does the same.

A save with no conflicts left deletes the session file.

Closing with unsaved edits

Section titled “Closing with unsaved edits”

Closing the window or a tab with edits you have not saved asks first, under Exit with unsaved edits or Close with unsaved edits. Discard & exit or Discard & close drops the edits; Keep open goes back.

Encoding

Section titled “Encoding”

The Workbench writes UTF-8.

  • Manuscripts are cleaned of the stray characters the driver removes, such as a second byte-order mark, and get one byte-order mark or none: whatever ours and theirs agree on, or when they differ, whatever the side that changed from base has. When something was removed, the ribbon says so after saving.
  • A text merge under git mergetool keeps ours’ own encoding and byte-order mark.
  • Other files saved from the start screen are written as UTF-8 without a byte-order mark.
