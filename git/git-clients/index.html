Git clients

git never opens a merge tool on its own. When you run git merge, the XML merge driver runs automatically on every .xml file. It applies its XML rules to Duck Creek manuscripts (root element <ManuScript>) and gives every other file git’s normal line merge. If a conflict is left, git stops and waits. The Workbench opens only when you, or your git client, ask for it. It opens any conflicted file; one that is not a manuscript opens as a text merge, with a note saying why.

If a manuscript carries stray characters around its content, such as a second byte-order mark, the driver removes them and prints a line starting with MXmlBench: that names the side, by the label git gives it. When the Workbench opens the file, its ribbon says what it removed from ours or theirs, for example Removed a second byte-order mark before the root from ours. The saved file will start with one byte-order mark.

How you ask depends on the client. Some use git’s own merge tool setting, which setup already pointed at M-XML Bench, so they need nothing more. Others keep their own setting, and you enter M-XML Bench there once.

The arguments

Section titled “The arguments”
Argument Required Gets
--base <file> Yes The common ancestor. An empty file is fine; that means both sides added the file.
--ours <file> Yes Your side (git’s LOCAL)
--theirs <file> Yes The side being merged in (git’s REMOTE)
--output <file> Yes Where to write the result (git’s MERGED)
--label-ours <text> No A name for the ours pane
--label-theirs <text> No A name for the theirs pane

Exit codes

Section titled “Exit codes”

The Workbench exits with 0 only after Save & finish has written a fully resolved file. It exits 1 when you close without writing or choose Keep for later, and 2 for bad arguments or an error. Where a client offers to trust the exit code, turn that on, so the client marks the file resolved only when it really is.

Clients that use git’s setting

Section titled “Clients that use git’s setting”

These follow git’s own merge tool setting, so you never enter M-XML Bench in them. VS Code needs one extension first.

git command line

Section titled “git command line”

If another tool is your default, git mergetool --tool mxmlbench still opens M-XML Bench.

VS Code

Section titled “VS Code”

VS Code’s built-in merge editor only resolves conflicts itself; it has no setting to call an outside tool. The Git Diff and Merge Tool extension adds one.

  1. Install Git Diff and Merge Tool (david-rickard.git-diff-and-merge-tool).
  2. In the Source Control view, right-click a file under Merge Changes and choose Launch merge tool.

The extension runs git mergetool -y <file> for you, so git’s setting decides which tool opens. It runs without a terminal and cannot answer git’s “was the merge successful?” question. The installer’s trustExitCode = true setting answers it for you. The extension was last updated in 2021.

Note

You can also run git mergetool in VS Code’s integrated terminal. That needs no extension.

Sources: marketplace page, extension source, VS Code merge conflicts.

Git Extensions

Section titled “Git Extensions”

Git Extensions reads the merge tool from git’s config (Settings > Git > Config, Mergetool), so it picks up mxmlbench automatically. It checks merge.guitool before merge.tool, so if you have set a GUI tool there, that one wins.

After a merge stops on conflicts, Git Extensions opens its resolve conflicts dialog, or asks first, depending on Settings > Confirmations. Double-click a file there to open the Workbench. When the Workbench exits 0 and the file has changed, Git Extensions stages it.

Sources: settings, merge conflicts.

Fork

Section titled “Fork”

Fork 2.4 and later support custom merge tools under Preferences > Integration. Point a custom merge tool at the Workbench path with the same arguments as Sourcetree.

An open Fork issue reports that a file can stay marked conflicted after a custom tool exits cleanly. If that happens, mark it resolved in Fork yourself.

Source: Fork release notes.

Clients that use their own merge editor

Section titled “Clients that use their own merge editor”

These clients’ documentation does not describe opening an outside merge tool for a conflict. For these, run git mergetool in a terminal instead of resolving in the client.

Client What its docs say
GitHub Desktop No outside merge tools. The request is marked not planned.
GitKraken Desktop Merge tools are picked from a fixed list.
Visual Studio Conflicts are resolved in its own Merge Editor. Run git mergetool from View > Terminal.

During a rebase

Section titled “During a rebase”

Every client passes git’s names straight through, so the ours and theirs panes read the other way around during a rebase. The Quick start explains why.
